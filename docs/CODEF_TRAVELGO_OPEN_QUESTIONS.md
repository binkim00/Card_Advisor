# CODEF 계정 인증·트래블GO 취소 규칙 확인 — 2026-10-22

## 공식 자료와 이번 결정
- CODEF [계정 등록](https://developer.codef.io/cert/account/cid-register)·[계정 수정](https://developer.codef.io/cert/account/cid-update): 공개 가이드 원문에서 `accountList` 항목의 `cardNo`, `cardPassword`를 확인했다. KB의 카드 소지 확인 요구 시 전체 카드번호와 RSA 암호화한 비밀번호 앞 2자리다. 일반 등록의 필수값이나 CF-03002 이어가기라고 해석하지 않는다.
- 공개 콘텐츠는 공식 사이트가 사용하는 `https://admin.codef.io/dev-guide-menu/menu-detail/cid-register?mode=real` 및 `cid-update`로도 대조했다. 로그인/키/개인정보를 사용하지 않았다.
- [CODEF 공통 추가 인증](https://developer.codef.io/common-guide/add-auth)은 상품별 상세 파라미터 확인을 요구한다. 공개 계정 등록·수정 문서에는 `is2Way`/`twoWayInfo`/`method`의 계정별 배치나 다중 계정 재개 예제가 없다. 일반 조회의 프로토콜을 복사하지 않았다.
- [하나 트래블GO 체크카드 계좌형 공식 설명서](https://m.hanacard.co.kr/leaflet/15/15252_20250115.pdf): 일반 실적은 전월 승인 기준이고, 취소 접수 월에 적립된 하나머니를 차감한다. 후자는 적립금 회수 규칙으로만 확인했다. 취소 실적 귀속과 한도·횟수 복원 규칙으로 확장하지 않았다. 검색된 다른 카드 및 이벤트 약관은 이 상품의 상시 혜택에 적용하지 않았다.

## CODEF 구현·검증
연결 생성/실패 후 재요청/재인증 API와 Android에 KB 선택형 소지 확인을 연결했다. 명시적 추가 동의, 기관 제한, 입력 검증, 화면 마스킹·보안 창, 백그라운드/이탈/제출 시 삭제. 인증값은 DB·응답·로그에 남기지 않는다. provider 입력은 accountList 내부이며 카드 비밀번호는 RSA로 암호화한다. 없는 선택 필드는 생략해 기존 요청의 멱등 해시 형식을 유지한다.

계정 errorList 내부 CF-03002도 실패/자동 재시도 대상으로 취급하지 않는다. 계정 추가 인증 대기 중에는 최소 3분 재인증·해제를 차단한다. 이 제한은 공통 안내를 따른 보수적 기본값이며 기관별 제한 확정은 아니다. Connected ID 없는 생성 보류를 신규 생성이나 삭제로 우회하지 않는다.

계약51·PG22·API 문서 포함78 검사 통과(실패/오류/skip0), `.run/account-ownership-test.log`. Android JVM·lint·debug/androidTest/unsigned release 빌드 통과, `.run/account-ownership-android-build.log`. 에뮬레이터에서 마스킹·백그라운드 삭제→생성→재인증→재시작 조회→HTTP→격리 PostgreSQL 연결1/요청2 확인. `.run/ownership-android.json`, `.run/account-ownership-emulator.log`. 실제 외부기관 호출0·물리기기 검사0. 사용자 DB54329와 로그인은 이 검증에 사용하지 않았다.

## 확인에 필요한 정확한 정보

### CODEF 개발 지원에 확인할 항목
대상은 KR/CD/P, KB0301·하나0313, ID/PW 방식의 `/v1/account/create`와 `/v1/account/update`이다. 비밀키·실제 ID/PW·카드번호가 아닌 규격/합성 예제로 답변받는다.
1. 계정 관리도 CF-03002 다단계 재개를 지원하는지. 지원 환경(DEMO/PRODUCTION), 기관별 method, 같은 endpoint 여부.
2. 인증 식별자·method·인증 응답값이 최상위인지 각 accountList 항목인지, errorList와 어느 계정을 연결하는지. 1차/2차/다음 차수의 요청·응답 합성 예제와 필드 형식.
3. 이어가기 시 원래 ID/PW 또는 인증서 재전송 필요 여부, Connected ID 생성 시점, 일부 성공/실패와 응답 유실의 계정 등록 여부를 확인하는 방법.
4. 실제 제한시간·만료 코드, 재시도/중복 인증 허용 조건, 중단·해제 API 지원 여부.
5. KB 소지 확인을 요구하는 정확한 오류 코드와 최초/실패 후 제출 시점. 공개 문서의 선택 필드 존재만으로 특정 실패를 소지 확인 요구라고 단정하지 않는다.
