단위: 순수 계산·규칙 경계 → 통합: 실제 PostgreSQL 제약·트랜잭션·중복 → 계약: OpenAPI/Android DTO/공급자 매핑 → E2E: 사용자 흐름 → 실기기: 지원 주문 경로 → 외부 연동: 허용된 본인 데이터 → 배포: 심사/설치.

## 속성 기반·경계 검사
혜택 ≥0, 적용된 각 한도 이하, 순취소액≤원승인, 추천 조회 전후 원장 동일, 동일 입력 동일 결과, 카드 배열 순서가 비동률 순위에 영향 없음, 지원 최소금액 직전/정확히/직후, KST 월말23:59:59와 다음월00:00:00.
금액 증가가 항상 혜택 증가를 보장하는 것은 아니므로 약관에 없는 단조성 가정을 테스트로 강제하지 않는다.
## 데이터 준비
3개 실제 지원 카드 각각 적용 가능한 경계·제외·한도·취소·할부·경로 사례를 최소10건 이상 작성한다. 가상 G01~G12는 엔진 기본 검증용이며 실제 카드 약관 검증을 대체하지 않는다.
DB 통합 테스트는 PostgreSQL로 수행한다. SQLite 또는 메모리 DB 통과를 원장 제약·트랜잭션 검증으로 대체하지 않는다. 외부 API는 합성 응답 계약 테스트와 허용된 본인 실데이터 대조를 구분한다.
## 실제 기기 기록
기기/OS/앱/adapter 버전, 지원 경로, 테스트 케이스, 표시된 정답액, 추출액, confirmation 상태, 지연, 판정, 민감정보 제거 증거를 남긴다. 주문서 감지는 결제 전까지만 검증 가능하다. 실제 승인·취소가 필요하면 원래 예정된 본인 구매 내역으로 확인하고 검증을 위한 추가 소비를 강제하지 않는다.
## 성능 계획
카드5개·규칙100개·원장1만건 합성 데이터, 권장 서버 사양을 기록하고 추천100회 워밍업 후1,000회 측정. p50/p95/p99와 오류율, 쿼리 수를 기록한다. 목표는01 문서 기준이며 측정 없이 충족으로 표기하지 않는다.
## 출시 게이트
- G0: 범위·보유카드·공급자 이용 조건·지원 경로 선택 근거.
- G1: 결정적 계산·금액 경계·버전·예산 사례 전부 통과 → M0.
- G2: 본인 금융 연결·중복/취소 정합성·실제 카드3종·소유권·삭제 통과.
- G3: 최소 한 쇼핑몰 실제 기기 감지 통과 + G2 → M1.
- G4: 두 번째 쇼핑몰·AI 평가 → M2.
- G5: 스토어 고지/데이터안전/접근성 신고/실제 설치 점검 → M3. 제출·승인·사용 가능 상태를 각각 기록.
원 단위 계산 오류, 타 사용자 데이터 접근, 인증정보 누출, 오래된 금액 추천 유지, 삭제 후 재수집은 출시 차단 결함이다. P1을 미룰 수 있으나 P0 실패를 완료로 바꾸지 않는다.
## 증거 기록 양식
TC-ID / 실행일 / build·API·ruleset·adapter 버전 / 입력 fixture / 기대값 / 실제값 / 판정 / 증거 링크 / 알려진 제한. 민감 원문 로그를 노션에 붙이지 않는다. 현재 결과 칸은 전부 ‘미실행’이다.
